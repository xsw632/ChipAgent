**2. Fix `hooks/hooks.json`** -- add a script-level guard.

The research recommends keeping the hook (useful for manual Scala edits) but preventing it from firing on non-Scala writes. Since `hooks.json` does not support file-path matchers, the fix goes in the hook command itself. Replace the command with a wrapper that checks the file extension:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "bash -c 'FILE=\"${CLAUDE_TOOL_INPUT_FILE:-}\"; case \"$FILE\" in *.scala) ${CLAUDE_PLUGIN_ROOT}/scripts/compile.sh ;; esac'",
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

If `CLAUDE_TOOL_INPUT_FILE` is not available in the hook environment (Claude Code may not expose it), use a simpler guard: check if any `.scala` file in `chisel-project/src/` was modified more recently than the last compilation output. However, the simplest reliable approach per the research is: remove the hook entirely since the orchestrator now calls compile.sh explicitly, and standalone compile is available via `/chip-agent:compile`. The hook was a v1.0 convenience that is now superseded.

Preferred approach (per research open question #1): **Keep the hook but make the command a no-op** by wrapping with a guard. If the hook environment does not provide the file path, the safest fix is to update the command to exit early unless the script detects a Scala file change. The research recommends checking `HOOK_FILE` but notes this may not exist. Test which environment variables are available.

Final fallback: If no file-path variable is available in the hook environment, remove the PostToolUse section entirely from hooks.json (leave an empty hooks object). The orchestrator and standalone skills handle compilation explicitly.
