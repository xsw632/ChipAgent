# Milestone v1.2.0: Smart Retry & QoR Optimization

**Status:** SHIPPED 2026-04-02
**Phases:** 16-17
**Total Plans:** 4

## Overview

Added intelligent failure diagnosis, error-type-based parameter retry, and multi-round QoR optimization to the MCP-driven PnR pipeline. Three new MCP tools (diagnose_failure, clean_design, compare_runs) plus generate_config extension provide the backend infrastructure, while the PnR skill orchestrates a 3-round retry loop with stage-aware restart and QoR comparison table.

## Phases

### Phase 16: Diagnosis & Retry Infrastructure

**Goal**: MCP server provides all tools needed to diagnose failures, clean cached state, and regenerate configs with tuned parameters
**Depends on**: Phase 15 (existing MCP server and ORFS pipeline)
**Plans**: 2 plans

Plans:
- [x] 16-01: diagnose_failure MCP tool with 5-type error classification, silent timing detection, and bounded parameter suggestions
- [x] 16-02: clean_design tool with 30s timeout, generate_config tuning extension, MCP server registration

**Key Decisions:**
- Classification priority: synthesis > placement_overflow > congestion > drc > timing_violation > unknown
- Sequential vs combinational timing distinguished by SDC virtual_clk pattern
- 30-second timeout for clean_design (fast operation; long runtime signals failure)
- Optional tuning params omitted from config.mk when undefined (backward compatible)

### Phase 17: Retry Orchestration & QoR Optimization

**Goal**: PnR skill automatically retries failed flows with diagnosed parameter adjustments and presents multi-round QoR comparison with best-run recommendation
**Depends on**: Phase 16 (diagnosis and retry tools available)
**Plans**: 2 plans

Plans:
- [x] 17-01: compare_runs MCP tool with JSON persistence, 4 actions (save/load/recommend/clear), deterministic best-run selection
- [x] 17-02: PnR skill retry loop with stage-aware restart, QoR comparison table, best-run recommendation

**Key Decisions:**
- recommendBest uses deterministic filter+sort (not LLM judgment) for reliable best-run selection
- Four actions (save/load/recommend/clear) in single tool for cohesion
- Flat file JSON for qor_history.json -- sufficient for <10 runs per design
- Retry loop uses mutable current_params that accumulate adjustments across rounds
- Critical severity errors abort retry immediately -- synthesis and combinational timing not parameter-fixable
- clean_design mandatory before every retry to prevent ORFS stale cache

## Milestone Summary

**Key Decisions:**
- Error classification via regex priority chain with structured DiagnosisResult return type
- Parameter suggestion with min/max clamping to prevent unreasonable values (clock [1.0, 100.0], density [0.30, 0.85], utilization [20, 70])
- QorRun interface with readonly Record<string, unknown> for flexible schema
- Read-append-write pattern for atomic JSON persistence
- Stage-aware restart via STAGE_ORDER slice from diagnosis restart_from
- Retry orchestration in Skill layer (not MCP server) for flexibility

**Issues Resolved:**
- Silent timing violations (WNS < 0 despite all stages succeeding) now detected by diagnose_failure
- ORFS stale cache invalidation handled by mandatory clean_design before retries

**Issues Deferred:**
- ORFS error regex patterns need validation against actual sky130hd log output
- Hold violation detection not yet in existing get_report
- Pareto-optimal run selection (OPT-01) deferred to future milestone
- Docker mode support (OPT-04) deferred

**Technical Debt Incurred:**
- Regex-based error classification may miss edge cases in untested ORFS versions
