# CPU Testing Strategy for ChipAgent

## Problem Statement

ChipAgent's existing testbench pattern (struct-based test vectors, single `eval()`) works for combinational modules (ALU, decoders) but cannot verify sequential CPU modules that execute instructions over multiple clock cycles.

A CPU testing strategy must:
- (a) Be reliably generated by an LLM -- minimize surface area for encoding errors
- (b) Catch real bugs -- compare DUT behavior against a known-correct reference
- (c) Scale to the full RV32I instruction set (~40 unique instructions)

## Three-Tier Verification Approach

| Tier | Module Type | Strategy | Example |
|------|-------------|----------|---------|
| Simple struct | Combinational (ALU, mux) | TestCase struct with expected values, single eval() | Existing `sim/tb_ALU.cpp` |
| Reference model | CPU/processor | Embedded C++ RV32I emulator, cycle-by-cycle comparison | New `sim/cpu_test_template.h` |
| Formal (future) | Critical paths | Property-based verification | Not implemented |

## Strategies Considered

### 1. Hand-written golden vectors

Manually encode the expected register state after each instruction.

- **Pros:** Simple to understand, no additional infrastructure
- **Cons:** Error-prone at scale; the LLM must correctly compute expected values for each test; combinatorial explosion for multi-instruction sequences; any mistake in the expected value causes a false failure

### 2. ISA simulator comparison (Spike / riscv-isa-sim)

Run an external ISA simulator (Spike) alongside the DUT, comparing state after each instruction.

- **Pros:** Gold standard for RISC-V verification; well-tested reference implementation
- **Cons:** Requires external tool installation (Spike); complex integration with Verilator; not portable across developer environments; adds significant setup complexity

### 3. Embedded reference model (CHOSEN)

A ~150-line C++ RV32I emulator embedded directly in the testbench header file.

- **Pros:** Self-contained (no external dependencies); LLM only composes test sequences using helper functions; reference model is fixed/audited, not regenerated per run; catches LLM encoding errors automatically
- **Cons:** Reference model must be correct (but it is a fixed, reviewed artifact); limited to RV32I (extensible to RV32IM by adding M-extension cases)

## Decision: Embedded C++ Reference Model

**Rationale:** The LLM's job is reduced to composing instruction sequences using provided helper functions. The fixed template handles encoding, emulation, and comparison. This minimizes the surface area for LLM errors -- the most common failure mode.

The reference model (`sim/cpu_test_template.h`) is a fixed artifact that ships with ChipAgent. It is not generated per run. This means:
- Encoding bugs in the reference model are caught once during development, not repeatedly
- The LLM never needs to write an emulator or compute expected register values
- Test failures indicate either a DUT bug (Chisel generation issue) or a test sequence issue

## Debug Ports

Complex CPU modules always include these debug ports in their IO bundle:

| Port | Direction | Width | Purpose |
|------|-----------|-------|---------|
| `debug_pc` | Output | 32 bits | Current program counter value |
| `debug_reg_addr` | Input | 5 bits | Register address to observe (driven by testbench) |
| `debug_reg_data` | Output | 32 bits | Value of the register at `debug_reg_addr` |

These allow the testbench to observe internal CPU state without modifying the datapath. The testbench drives `debug_reg_addr` to select which register to read, then compares `debug_reg_data` against the reference model's register file.

Debug ports can be stripped for synthesis but are mandatory for verification.

## Instruction Encoding Helpers

Fixed `constexpr` functions eliminate the most common LLM error -- incorrect bit-field encoding:

| Function | Format | Instructions |
|----------|--------|-------------|
| `r_type(funct7, rs2, rs1, funct3, rd)` | R-type | ADD, SUB, AND, OR, XOR, SLT, SLL, SRL, SRA |
| `i_type(imm, rs1, funct3, rd, opcode)` | I-type | ADDI, LW, JALR |
| `s_type(imm, rs2, rs1, funct3)` | S-type | SW, SH, SB |
| `b_type(imm, rs2, rs1, funct3)` | B-type | BEQ, BNE, BLT, BGE |
| `u_type(imm, rd, opcode)` | U-type | LUI, AUIPC |
| `j_type(imm, rd)` | J-type | JAL |

Convenience wrappers (`rv_add()`, `rv_addi()`, `rv_sub()`, etc.) make test code readable:

```cpp
// Instead of manually encoding: 0x003100B3
uint32_t inst = rv_add(1, 2, 3);  // ADD x1, x2, x3
```

## Test Coverage: Per-Instruction Smoke Tests

Target: ~40 tests covering each RV32I instruction type with 2-3 vectors per instruction.

| Category | Instructions | Count | Vectors |
|----------|-------------|-------|---------|
| R-type arithmetic | ADD, SUB, AND, OR, XOR, SLT, SLL, SRL, SRA | 9 | 18 |
| I-type immediate | ADDI, ANDI, ORI, XORI, SLTI, SLLI, SRLI, SRAI | 8 | 8 |
| Load/Store | LW, SW | 2 | 4 |
| Branch | BEQ, BNE, BLT, BGE, BLTU, BGEU | 6 | 6 |
| Jump | JAL, JALR | 2 | 4 |
| Upper immediate | LUI, AUIPC | 2 | 3 |
| **Total** | | **29** | **~43** |

Each test includes one basic case and one edge case (overflow, zero, negative, boundary conditions).

## LLM Generation Considerations

- The LLM receives the fixed template (`cpu_test_template.h`) and only writes the test sequence composition
- Instruction encoding is done via helper function calls, not raw hex values
- The reference model runs identically to the DUT, so expected values are computed, not hand-specified
- If a test fails, it indicates either a DUT bug (Chisel generation issue) or a test sequence issue (fixable by regenerating the test)
- The testbench pattern follows the same output format (`[TEST N] ... PASS/FAIL`, `RESULT: PASSED/FAILED X/Y tests`) as the simple struct-based testbenches
